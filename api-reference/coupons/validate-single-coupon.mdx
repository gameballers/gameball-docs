This API validates a single coupon identified by `{code}` and checks its eligibility for use by a customer. You can also describe the cart, so the coupon's rules are checked against what the customer is actually buying, and set `lock` to `true` to reserve the coupon so it cannot be spent elsewhere while the order is being completed.

Available on **v4.0** and **v4.1**. Requires the **Gameball Coupon Engine** feature on your plan — accounts without it are rejected before any validation runs.

There are two ways to burn a coupon when placing an order:

- **Option 1 — Use the coupon code directly in the Order API**: Pass the coupon code in the Order API without needing the lock reference. The coupon burns automatically.
- **Option 2 — Use the lock reference in the Order API**: Pass the `lockReference` from this API into `redemption.couponsLockReference` in the Order API. The coupon burns automatically — no separate Burn Coupon API call is needed.

<Warning>
If you validate a coupon with `lock: true` and then call the **Release Coupons API** before placing the order, the lock is released. If you then try to use the coupon code directly in the Order API, the request will fail. Only release the lock if you are canceling the transaction entirely.
</Warning>

<Info>
To validate several coupon codes against the same cart in one call, use [Validate Multiple Coupons](/api-reference/coupons/validate-multiple-coupons).
</Info>

<Info>
**Channel Merging Available**  
If your system uses different customer IDs across multiple channels (e.g., online and offline), Gameball's channel merging feature helps unify customer profiles. By including the customer's mobile number or email (based on your merging configuration) with each request, Gameball will combine activities into a single profile.

For more information, head to the [Omni-Channel Handling Guide](/tutorials/experiences/more/omni-channel).
</Info>

<Info>
**Security**: Requires **apikey** and **secretkey** headers.
</Info>

## Describing the cart

A coupon's rules are only enforced when the request describes a cart, and whether it does is decided from **that coupon's own rules** — see [Eligibility checks](#eligibility-checks). The fields that describe a cart fall into two groups, and the group decides how a rule on that field behaves.

| Group | Fields | Behaviour |
| :--- | :--- | :--- |
| **Cart-level** | `merchantId`, `branchId`, `channel`, `extra`, `totalPurchaseAmount` | Describe the order as a whole — one merchant, one branch, one sales channel. They have no per-item form. |
| **Item-level — flat** | `collectionId`, `collectionsIds` | The collections the basket touches, without saying which item is in which. |
| **Item-level — lines** | `lineItems[]` | The cart described item by item, including the item fields that have no flat form, such as `categories`, `productId`, `price`, `quantity` and `tags`. |

<Warning>
Send `lineItems` **or** the flat collection fields, not both. When `lineItems` is present, the top-level `collectionId` and `collectionsIds` are ignored for matching — put every collection on the lines instead. Categories and products are only ever sent on the lines. The cart-level fields are always read from the top of the body.
</Warning>

### Line item fields

| Field | Type | Read by the rule |
| :--- | :--- | :--- |
| `productId` | string | `ProductId`, and the cart-level `TotalUniqueItems` |
| `variantId` | string | None — stored and echoed back, but **never evaluated** |
| `categories` | string[] | `Category` |
| `collectionsIds` | string[] | `Collection` |
| `title` | string | `Title` |
| `price` | number | `Price` |
| `quantity` | number | `Quantity`, and the cart-level `TotalItems` |
| `discount` | number | `Discount` |
| `vendor` | string | `Vendor` |
| `sku` | string | `Sku` |
| `tags` | string[] | `Tags` |
| `weight` | number | `Weight` |
| `extra` | object | `ItemExtra.<key>` |

Only `collectionsIds` has a flat form. A rule on any other item field — including `Category` and `ProductId` — can only be satisfied through `lineItems`.

### Extra data

`extra` at the top of the body and `extra` on each line carry free-form data for rules on fields Gameball has no named field for — a payment method, a delivery city, a gift-wrap flag. The rule names the key to read after its prefix:

| Rule | Reads |
| :--- | :--- |
| `Extra.paymentMethod` | `extra.paymentMethod` |
| `Extra.shipping.city` | `extra.shipping.city` — nested keys are separated by dots |
| `ItemExtra.giftWrap` | `lineItems[].extra.giftWrap` |

Send each key exactly as it is spelled in the rule. A key that is missing, `null`, a blank string or an empty list counts as not sent.

### Size limits

| Field | Limit |
| :--- | :--- |
| `lineItems` | 500 entries |
| `collectionsIds`, and `categories`, `collectionsIds` and `tags` on each line | 200 values per list |
| `channel` | 100 characters |
| `lineItems[].productId`, `lineItems[].variantId` | 100 characters |
| `lineItems[].vendor`, `lineItems[].sku` | 255 characters |

A request over any limit is rejected with `400`.

## Example request

```bash cURL
curl --request POST \
  --url 'https://api.gameball.co/api/v4.0/integrations/coupons/SONYAUDIO/validate' \
  --header 'APIKey: <your-api-key>' \
  --header 'secretkey: <your-secret-key>' \
  --header 'Content-Type: application/json' \
  --data '{
    "customerId": "omar-9912",
    "lock": true,
    "lockDuration": 30,
    "merchantId": "cairo-downtown",
    "branchId": "branch-14",
    "channel": "online",
    "totalPurchaseAmount": 1450.0,
    "extra": {
      "paymentMethod": "card"
    },
    "lineItems": [
      {
        "productId": "p-sony-bravia",
        "variantId": "v-55in",
        "title": "Sony Bravia 55-inch TV",
        "price": 1200.0,
        "quantity": 1,
        "vendor": "Sony",
        "sku": "KD-55X80L",
        "categories": ["TV"],
        "collectionsIds": ["electronics"],
        "tags": ["4k"]
      },
      {
        "productId": "p-sony-wh1000",
        "variantId": "v-black",
        "title": "Sony WH-1000XM5 Headphones",
        "price": 250.0,
        "quantity": 1,
        "vendor": "Sony",
        "sku": "WH1000XM5-B",
        "categories": ["Audio"],
        "collectionsIds": ["electronics", "headphones"],
        "tags": ["wireless", "noise-cancelling"]
      }
    ]
  }'
```

The coupon's operator is `AND`, so the order must be with `cairo-downtown`, on the `online` or `app` channel, and not paid in cash — and one single line must be an Audio item from Sony priced at 100 or more. The headphones line satisfies all three item rules; the television does not need to.

## How validation works

A validate call answers three questions in order. The first failure ends the call — you get one error, never a list.

<Steps>
  <Step title="Is the customer real and active in your Gameball program?">
    Resolved from `customerId`, `email` or `mobile`.
  </Step>
  <Step title="If you referenced an existing lock, is it still usable by this customer?">
    Resolved from `lockReference`.
  </Step>
  <Step title="Does the coupon exist, does it apply to this cart, and may this customer use it?">
    Runs the ordered checks below.
  </Step>
</Steps>

The third question runs these checks in this exact order. The order matters: a coupon that is both expired *and* wrong for the cart reports the cart problem, because rules are checked first.

| Order | Check | Error |
| :--- | :--- | :--- |
| 1 | The coupon code exists for your account | `404`, code `4004` |
| 2 | The coupon's rules match the cart | See [Rule errors](#rule-errors) |
| 3 | `totalPurchaseAmount` is present and at or above the coupon's `minOrderValue` | `9017` |
| 4 | The coupon is active | `9014` |
| 5 | The coupon's start date has passed | `9011` |
| 6 | The coupon has not expired | `9013` |
| 7 | The customer is in the coupon's audience, and the coupon is not assigned to a different customer | `9011` |
| 8 | The customer has not hit the coupon's per-customer limit | `9012` |
| 9 | The coupon has not hit its total usage limit | `9012` |

## Coupon rules

Every restriction a coupon carries is a **rule**: the field it reads, an operator, and the values to compare with. Rules are configured on the coupon in the Gameball dashboard, and the validate response returns them on `rules`.

| Property | Meaning |
| :--- | :--- |
| `name` | The field the rule reads — see [Rule fields](#rule-fields). |
| `operator` | How the cart's value is compared — see [Operators](#operators). |
| `matchValue` | The values to compare with, comma-separated. Empty for the operators that only check whether a value is there. |

`rules` is `null` on a coupon configured without rules. Such a coupon is matched against its `entitled*` lists exactly as before, each list acting as an `Equals` rule.

<Note>
On a coupon configured with rules, the `entitled*` lists hold only the values of its **`Equals`** rules on merchant, branch, collection, category and product. A rule with any other operator, and every rule on the other fields, appears in `rules` only. Read `rules` for the full picture.
</Note>

### Rule fields

| `name` | Level | Read from |
| :--- | :--- | :--- |
| `Merchant` | Cart | `merchantId` |
| `Branch` | Cart | `branchId` |
| `Channel` | Cart | `channel` |
| `TotalItems` | Cart | The sum of `lineItems[].quantity` — a line without a quantity counts as 1 |
| `TotalUniqueItems` | Cart | The number of distinct `lineItems[].productId` values |
| `Extra.<key>` | Cart | `extra.<key>` |
| `Collection` | Item | `lineItems[].collectionsIds`, or `collectionId` and `collectionsIds` |
| `Category` | Item | `lineItems[].categories` |
| `ProductId` | Item | `lineItems[].productId` |
| `Title` | Item | `lineItems[].title` |
| `Price` | Item | `lineItems[].price` |
| `Quantity` | Item | `lineItems[].quantity` |
| `Discount` | Item | `lineItems[].discount` |
| `Vendor` | Item | `lineItems[].vendor` |
| `Sku` | Item | `lineItems[].sku` |
| `Tags` | Item | `lineItems[].tags` |
| `Weight` | Item | `lineItems[].weight` |
| `ItemExtra.<key>` | Item | `lineItems[].extra.<key>` |

A cart-level rule is checked once, against the order. An item-level rule is checked against each line. `TotalItems` and `TotalUniqueItems` are worked out from `lineItems`, so a coupon with either rule needs the cart sent line by line.

### Operators

| `operator` | Satisfied when the cart's value | `matchValue` |
| :--- | :--- | :--- |
| `Equals` | equals any of the values | One or more values |
| `NotEquals` | equals none of the values | One or more values |
| `Contains` | contains any of the values as text | One or more values |
| `NotContains` | contains none of the values as text | One or more values |
| `StartsWith` | starts with any of the values | One or more values |
| `EndsWith` | ends with any of the values | One or more values |
| `GreaterThan` | is greater than the number | Exactly one number |
| `GreaterThanOrEqual` | is greater than or equal to the number | Exactly one number |
| `LessThan` | is less than the number | Exactly one number |
| `LessThanOrEqual` | is less than or equal to the number | Exactly one number |
| `Between` | is between the two numbers, both included | Two numbers, `min,max` |
| `Exists` | was sent | Empty |
| `NotExists` | was not sent | Empty |
| `IsEmpty` | was not sent, or is blank or an empty list | Empty |
| `NotEmpty` | was sent and is not blank or an empty list | Empty |

- Text is compared **case-insensitively**, and surrounding whitespace is trimmed. Coupon codes are compared the same way.
- On a field that holds a list — `categories`, `collectionsIds`, `tags` — `Equals` is satisfied when any entry matches any value, and `NotEquals` when no entry matches any of them.
- `Equals` with a single number compares numerically, so `100` matches `100.0`.
- The numeric operators need a number on both sides. A value that is not a number never satisfies them.
- A value the request did not send satisfies only `NotExists` and `IsEmpty`.
- `collectionId` and `collectionsIds` are evaluated **together** as one list.
- `lineItems[].categories` are free-text names, not IDs — whatever was typed when the coupon was configured, compared as plain strings.

### How rules combine

`couponRulesLogicalOperator` is returned on the coupon object and tells you how **all** of its rules combine, cart-level and item-level alike.

| Value | Mode | Meaning |
| :--- | :--- | :--- |
| `"AND"` | AND | Every rule must be satisfied. Cart-level rules gate the order, and one **single line** must satisfy every item-level rule. Use this for coupons like "25% off Sony audio", which must not be satisfied by a Sony television plus another brand's headphones. |
| `"OR"` | OR | One satisfied rule is enough — cart-level or item-level. A rule the cart carries no data for is simply not satisfied; it is never rejected as missing. |
| `null` | Flat | Every rule must be satisfied, but not necessarily by the same line. Cart-level rules gate the order, and each item-level rule must be satisfied by some line. If the cart carries no data at all for a rule, the call is rejected. |

<Warning>
Under `OR`, merchant and branch are rules like any other, so they no longer gate the order on their own. An `OR` coupon with the rules *Merchant equals `cairo-downtown`* and *Category equals `Audio`* accepts an Audio item bought from any merchant. Use `AND` when the merchant must always match.
</Warning>

<Note>
`minOrderValue` is not a rule. It is set on the coupon's configuration and is enforced in every mode, including `OR` — see [The minimum order value](#the-minimum-order-value).
</Note>

### Item-level rules are satisfied line by line

An item-level rule is satisfied when **at least one line** satisfies it. For a negative operator, that means *at least one item lacks the value*, not *no item has it*: a rule *Category NotEquals `Sale`* is satisfied by a cart holding one sale item and one full-price item.

The flat collection fields describe the whole basket as one line. Sent as `"collectionsIds": ["sale", "shoes"]`, a cart fails a rule *Collection NotEquals `sale`* with `9021`, because the one line it describes holds `sale`.

### When lineItems is required

Send the cart as `lineItems` when either of these is true:

- **The coupon has a `Category` or `ProductId` rule.** Categories and products have no top-level field. Without `lineItems` the rule has no value to read, so it is reported as missing with `9026` or `9030` — or, under `OR`, simply not satisfied.
- **The coupon is `AND` and has two or more item-level rules.** One single line must satisfy all of them, which the flat collection fields cannot show. The call is rejected with `9032`; resend the same cart as `lineItems`.
- **The coupon has a rule on a field with no flat form** — `Title`, `Price`, `Quantity`, `Discount`, `Vendor`, `Sku`, `Tags`, `Weight`, `ItemExtra.<key>`, `TotalItems` or `TotalUniqueItems`. Without `lineItems` the rule has no value to read, so it is reported as missing with `9034` — or, under `OR`, simply not satisfied.

If you are unsure, send `lineItems` — it answers every case the flat lists do.

## Eligibility checks

Whether a call is a cart question or an eligibility question is decided **from the coupon's own rules**, not from which fields you happened to send.

The request describes a cart when it carries data for a field **one of this coupon's rules reads**. When it does, every rule the coupon holds is enforced — including ones the request said nothing about. When it does not, the call is an eligibility question — *"does this customer hold this coupon, and is it live?"* — and the rules are reported back on the coupon instead, so you can discover what to send next. Every other check (active, dates, audience, limits) runs either way.

A field no rule reads is ignored as though it were never sent. Sending `collectionsIds` to a coupon with no collection rule neither satisfies anything nor triggers anything.

| Coupon has rules on | Request carries | Outcome |
| :--- | :--- | :--- |
| Collection | `customerId` only | Eligibility — `valid: true` |
| Collection, no `minOrderValue` | `customerId`, `totalPurchaseAmount` | Eligibility — the amount matches no rule, so it is ignored |
| Collection | `collectionsIds` | Cart — the collection rule is enforced |
| Branch | `collectionsIds` | Eligibility — no rule on this coupon reads a collection |
| Channel, price (`AND` or flat) | `channel` | Cart — both are enforced, so the missing `price` is rejected with `9034` |
| Merchant, collection, product (`AND` or flat) | `merchantId`, `collectionsIds` | Cart — all three are enforced, so the absent product is rejected with `9030` |
| Collection, plus `minOrderValue` | `totalPurchaseAmount` | Cart — the amount speaks to the minimum, so the collection rule is enforced too |

<Note>
**A field you send that no rule reads is ignored.**

Request data is matched to rules **by field**. `collectionsIds` is only ever checked against a `Collection` rule, `merchantId` against a `Merchant` rule, `channel` against a `Channel` rule, `totalPurchaseAmount` against `minOrderValue`, and so on. When the coupon holds no rule on that field, the field is dropped before matching — it cannot satisfy a different rule, and it cannot cause a rejection.

The coupon below has a single rule, on collection. Every other field in the request corresponds to nothing on it, so all of them are discarded, the call stays an eligibility check, and it returns `valid: true`.

```json Request
{
  "customerId": "sara-1180",
  "merchantId": "cairo-downtown",
  "branchId": "branch-14",
  "channel": "online",
  "totalPurchaseAmount": 1450.0
}
```

```json Response
{
  "valid": true,
  "coupon": {
    "code": "winter25",
    "entitledCollectionIds": ["winter-24"],
    "entitledMerchantIds": null,
    "entitledBranchIds": null,
    "entitledCategoryIds": null,
    "entitledProductIds": null,
    "minOrderValue": null,
    "couponRulesLogicalOperator": "AND",
    "rules": [
      { "name": "Collection", "operator": "Equals", "matchValue": "winter-24" }
    ],
    "...": "..."
  },
  "lockReference": null,
  "dateToExpire": null
}
```

No collection was sent, and nothing else in the body speaks to a rule this coupon carries — so there is nothing to enforce, and nothing to reject. Send `collectionsIds` and the same call becomes a cart question.
</Note>

<Warning>
`valid: true` on an eligibility call means *"this customer may use this coupon"*, **not** *"this coupon applies to this order"*. Read `rules`, `couponRulesLogicalOperator` and `minOrderValue` off the response to see what the cart will have to satisfy — or, on a coupon without rules, `entitledCollectionIds`, `entitledCategoryIds`, `entitledBranchIds`, `entitledMerchantIds` and `entitledProductIds`. Then validate again with those fields populated before you complete the order. That second call can reject a coupon that just came back valid.
</Warning>

### The minimum order value

`minOrderValue` behaves like any other restriction. `totalPurchaseAmount` is matched against it and nothing else, so on a coupon with no `minOrderValue` the amount is ignored outright — it cannot make the call a cart question. On a coupon that has one, the amount is enough to describe a cart on its own, and the minimum is then enforced whether or not you sent a value.

| Coupon | Request describes a cart | `totalPurchaseAmount` | Result |
| :--- | :--- | :--- | :--- |
| `minOrderValue: 80` | Yes | `100` | Passes |
| `minOrderValue: 80` | Yes | `50` | `9017` |
| `minOrderValue: 80` | Yes | not sent | `9017` |
| `minOrderValue: 80` | No | not sent | Eligibility — not checked |
| `minOrderValue: null` | Either | anything | Not checked — there is no minimum to meet |

<Warning>
A cart that omits `totalPurchaseAmount` no longer slips past a coupon that has a `minOrderValue`. Both "you sent too little" and "you sent nothing" return `9017`; read the `message` to tell them apart.
</Warning>

## Locking a coupon

Set `lock` to `true` to reserve the coupon when it validates. The response carries a `lockReference` and a `dateToExpire`, and the coupon cannot be validated-and-locked by another order until the lock expires or is consumed.

<Note>
A coupon that is already locked still returns `valid: true` when this request does not lock it. Omit `lock`, `lockReference`, and `lockDuration` — for example, do not send `"lock": true`, `"lockReference": "123"`, and `"lockDuration": 1440`. Read `isLocked` on [Get Customer Coupons](/api-reference/customers/management/get-customer-coupons) to see the current lock state.
</Note>

| Setting | Effect |
| :--- | :--- |
| `lock: false` (default) | Validation only. `lockReference` and `dateToExpire` come back `null`. |
| `lock: true`, no `lockReference` | A new lock is created and its reference is returned. |
| `lock: true` with an existing `lockReference` | The existing lock is reused and the coupon is added to it. If the coupon is already in that lock, the lock is overwritten rather than rejected. |
| `lockDuration` | Overrides your account's default lock duration, in minutes. Must be greater than `0` and less than `21600` (15 days). |

When you pass an existing `lockReference` it is checked before anything else, and must be unused, unexpired and belong to the same customer — otherwise the call fails with `9009` or `9010`.

A lock is only ever created **after** the coupon has passed validation, so a returned `lockReference` always means the coupon was usable by that customer at that moment.

### Locking without a cart

You can lock on an eligibility check. Send only `customerId` with `lock: true` and no cart fields: a coupon that carries rules still validates — its rules are reported back rather than enforced — and it is still locked against that customer. The lock is built from the coupon code and the customer alone; the cart plays no part in it.

```json
{
  "customerId": "sara-1180",
  "lock": true,
  "lockDuration": 30
}
```

This is the intended way to reserve a coupon before the basket is known. Read `rules` and `couponRulesLogicalOperator` off the response to see what the cart will have to satisfy.

<Warning>
A cart-less lock does **not** prove the coupon fits the eventual cart. Rules were never evaluated, and nothing re-evaluates them later — not when the lock is reused, and not when the order is placed. Validate again with the full cart, reusing the same `lockReference`, before you complete the order: that re-runs the rule checks against the real basket and keeps the same lock.
</Warning>

## Errors

Errors use the standard Gameball [error envelope](/api-reference/overview/status-error-codes). The `message` names the specific values that failed, so it is the most useful field for diagnosing a rejection. It is returned in lower case.

```json
{
  "code": 9026,
  "type": "TRANSACTION_ERROR",
  "message": "this coupon requires a valid category to be applied. no category was provided.",
  "documentationUrl": "https://docs.gameball.co/api-reference/coupons/validate-single-coupon",
  "requestId": "3f9c21b8a4d7"
}
```

### By status

| Status | When |
| :--- | :--- |
| `400 Bad Request` | Invalid request payload, a missing required field, or a cart over the [size limits](#size-limits). |
| `401 Unauthorized` | Missing or invalid API key or secret key. |
| `404 Not Found` | The customer does not exist, the coupon code does not exist, or the `lockReference` does not exist. |
| `422 Unprocessable Entity` | The coupon exists but cannot be applied. |
| `429 Too Many Requests` | Rate limit exceeded. |
| `500 Internal Server Error` | An unexpected error occurred while validating. |

### Customer and request errors

| Code | Status | Meaning |
| :--- | :--- | :--- |
| `7000` | 404 | The customer was not found for the provided ID, email or mobile. |
| `3009` | 422 | The customer exists but is not active in your Gameball program. |
| `3000` | 400 | A required field is missing, the coupon code is empty, or the cart exceeded the size limits. |
| `4004` | 404 | The coupon code or `lockReference` does not exist. |

### Coupon eligibility errors

All `422`.

| Code | Meaning |
| :--- | :--- |
| `9011` | The coupon is not applicable — the customer is outside its audience, it is assigned to a different customer, or it has not started yet. |
| `9012` | A usage limit was reached — either the coupon's total limit or this customer's per-customer limit. |
| `9013` | The coupon has expired. |
| `9014` | The coupon is inactive. |
| `9017` | `totalPurchaseAmount` is below the coupon's `minOrderValue`, or the request described a cart and omitted it while the coupon has one. |

### Rule errors

All `422`. A *required* code means the coupon has a rule on that field and your request sent nothing for it. A *not eligible* code means you sent it and the value did not satisfy the rule.

| Code | Rule | Raised in |
| :--- | :--- | :--- |
| `9018` | Merchant — none provided | Flat and AND |
| `9019` | Merchant — not eligible | Flat, AND, and single-rule OR |
| `9024` | Branch — none provided | Flat and AND |
| `9025` | Branch — not eligible | Flat, AND, and single-rule OR |
| `9020` | Collection — none provided | Flat and AND |
| `9021` | Collection — not eligible | Flat, AND, and single-rule OR |
| `9026` | Category — none provided | Flat and AND |
| `9027` | Category — not eligible | Flat, AND, and single-rule OR |
| `9030` | Product — none provided | Flat and AND |
| `9031` | Product — not eligible | Flat, AND, and single-rule OR |
| `9034` | Any other field — none provided | Flat and AND |
| `9035` | Any other field — not eligible | Flat, AND, and single-rule OR |
| `9022` | Several rules were checked and none was satisfied | Multi-rule OR only |
| `9032` | The coupon must be evaluated against individual cart items — resend with `lineItems` | AND only |
| `9033` | `lineItems` was sent, every rule is met somewhere, but no single item meets them all | AND only |

An `OR` coupon never returns a *required* code — not even `9018` or `9024`. A rule the cart carries no data for is simply not satisfied. The presence operators (`Exists`, `NotExists`, `IsEmpty`, `NotEmpty`) never return one either, since a missing value is exactly what they test.

`9034` and `9035` cover every field without a code of its own, and the `message` names the field as you send it:

| Code | Example `message` |
| :--- | :--- |
| `9034` | `this coupon requires channel to be applied. it was not provided.` |
| `9035` | `this coupon is not eligible for the provided price (49.99, 1200).` |

The field reads `channel`, `extra.<key>`, `title`, `price`, `quantity`, `discount`, `vendor`, `sku`, `tags` or `weight`; `itemExtra.<key>` for a line's `extra`; and `lineItems` for the `TotalItems` and `TotalUniqueItems` rules. Because the message is lower-cased, a key such as `extra.paymentMethod` reads `extra.paymentmethod`.

### Lock errors

| Code | Status | Meaning |
| :--- | :--- | :--- |
| `9009` | 422 | The `lockReference` is invalid, has expired, or belongs to a different customer. |
| `9010` | 422 | The `lockReference` has already been used. |
| `9015` | 422 | `lockDuration` is negative. |
| `4000` | 400 | `lockDuration` is outside the permitted range — it must be greater than 0 and less than 21,600 minutes. |

<Note>
A `lockDuration` outside the permitted range is currently reported as the generic `4000` rather than the dedicated `9016`. Read the `message` for the specific reason.
</Note>

## What changed

### Rules with per-rule operators

Coupons now carry **rules**: each restriction reads one field, with its own operator. Rules can read new cart and line-item fields, and the coupon's operator now combines all of its rules — merchant and branch included.

| Area | Change |
| :--- | :--- |
| Request | New cart-level `channel` and `extra` |
| Request | New on each `lineItems[]` entry: `title`, `price`, `quantity`, `discount`, `vendor`, `sku`, `tags`, `weight` and `extra` |
| Response | New `rules` on the coupon |
| Response | `couponRulesLogicalOperator` is now a string — `"AND"` or `"OR"` — instead of `1` or `2` |
| Errors | New `422` codes: `9034` and `9035` |

<Warning>
**`couponRulesLogicalOperator` changed type.** It is now returned as `"AND"` or `"OR"`, where it used to be `1` or `2`. Code that reads it as a number must be updated. `null` is unchanged.
</Warning>

<AccordionGroup>
  <Accordion title="Behaviour changes on existing requests">
    These apply to every coupon, including ones configured before rules existed, with no change on your side.

    | What | Before | Now |
    | :--- | :--- | :--- |
    | An `OR` coupon restricted by merchant or branch | The merchant and branch always had to match | Merchant and branch are rules like any other — one satisfied rule is enough |
    | An `OR` coupon restricted by merchant or branch, where the cart omits that field | Rejected with `9018` or `9024` | Not rejected for the missing field; that rule is simply not satisfied |
    | An `OR` coupon with several rules, where the merchant or branch is wrong and nothing else matches | Rejected with `9019` or `9025` | Rejected with `9022` |
  </Accordion>

  <Accordion title="Migration notes">
    - **Read `couponRulesLogicalOperator` as a string.** Expect `"AND"`, `"OR"` or `null`.
    - **Read `rules` to see what the cart must satisfy.** On a coupon with rules, the `entitled*` lists show only its `Equals` rules on merchant, branch, collection, category and product.
    - **Send `lineItems` with the line fields your coupons' rules read** — `price`, `quantity`, `tags`, `sku` and so on. They have no flat form.
    - **Send `channel` and `extra` if your coupons' rules read them**, spelling each `extra` key exactly as the rule does.
    - **Handle `9034` and `9035`.** Read the `message` for the field that is missing or did not match.
    - **Review `OR` coupons that rely on a merchant or branch restriction.** Under `OR` it no longer gates the order on its own; switch those coupons to `AND`.
  </Accordion>
</AccordionGroup>

### Cart matching

Before coupon rules, this endpoint was extended from matching a coupon against two things only — the **merchant** and the **collection** — to four, and the request gained a line-by-line form of the cart.

| Area | Change |
| :--- | :--- |
| Request | New `branchId` and `lineItems[]` — categories and products are sent per line, as `lineItems[].categories` and `lineItems[].productId` |
| Response | New `entitledBranchIds`, `entitledCategoryIds` and `couponRulesLogicalOperator` |
| Response | `entitledProductIds` is no longer limited to a single value |
| Errors | New `422` codes: `9024`–`9027` and `9030`–`9033` |

<AccordionGroup>
  <Accordion title="Behaviour changes on existing requests">
    These affect calls you are already making, with no change on your side.

    | What | Before | Now |
    | :--- | :--- | :--- |
    | A coupon restricted by branch, category or product | The restriction was stored but not enforced | Enforced |
    | A coupon with two or more restrictions, where your cart described only one of them | Accepted | Rejected with the matching *required* code |
    | A coupon restricted by merchant, with `couponRulesLogicalOperator` set to OR | The wrong merchant could still pass if another restriction matched | The merchant had to match. Coupon rules changed this again — see [Rules with per-rule operators](#rules-with-per-rule-operators) |
    | Sending `collectionId` **and** `collectionsIds` together | Only `collectionsIds` was evaluated | Both are evaluated as one list |
    | A validate call sending **no** cart fields at all | Rejected with `9018` | Returns `200` with the coupon's restrictions attached |
  </Accordion>

  <Accordion title="Restriction matching is now decided per coupon">
    Previously any cart field switched on enforcement of **every** restriction the coupon held. A body carrying nothing but `customerId` and `totalPurchaseAmount` was enough to have a collection-restricted coupon rejected with `9020`, for a dimension the caller never meant to describe.

    Enforcement is now decided from the coupon's own restrictions. These affect calls you are already making, with no change on your side.

    | What | Before | Now |
    | :--- | :--- | :--- |
    | A cart field the coupon does not restrict on | Switched on enforcement of the coupon's other restrictions | Ignored as though it were never sent |
    | `totalPurchaseAmount` alone, coupon has no `minOrderValue` | Enforced every restriction; a restricted coupon was rejected | Eligibility check — `valid: true` with restrictions attached |
    | `totalPurchaseAmount` alone, coupon **has** a `minOrderValue` | Enforced every restriction | Unchanged — the amount speaks to the minimum, so it describes a cart |
    | A cart describing some of a coupon's restrictions | Enforced all of them | Unchanged — the missing ones still return their *required* code |
    | A cart omitting `totalPurchaseAmount`, coupon has a `minOrderValue` | Accepted — the minimum was skipped | Rejected with `9017` |
  </Accordion>

  <Accordion title="Migration notes">
    - **Add `branchId` if your coupons are branch-restricted.** There is no other way to satisfy a branch restriction.
    - **Send categories and products on `lineItems`.** There is no top-level field for either. When you send `lineItems`, put collections on the lines too — the top-level `collectionId` and `collectionsIds` are silently ignored when `lineItems` is present.
    - **Handle `9032` by retrying with `lineItems`.** It is not a permanent failure; it is a request for more detail about the same cart.
    - **API v3 cannot satisfy the new restrictions.** `POST /api/v3.0/integrations/coupons/{code}/validate` accepts only `merchantId` and `collectionId`, so a coupon restricted by branch, category, product or any of the newer rule fields is rejected with no field available to fix it. Move to v4 before configuring those restrictions.
  </Accordion>
</AccordionGroup>
